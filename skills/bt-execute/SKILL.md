Run tasks from a plan: build each one with its tests, have an independent verifier check it, and only then tick its box — and keep the feature's dashboard current as you go (see *Feature folder and dashboard*). Follow the project's agent instructions (AGENTS.md / CLAUDE.md / .github/copilot-instructions.md). The user's message after the skill name is the `arguments`.

```
/bt-execute [--auto-pilot] [--strict] [--verbose] [--no-time-limit] <plan> [task] [brief]

/bt-execute @.agents/specs/<slug>/documents/<slug>_plan.md ALL

/bt-execute @plan.md                         # NEXT: the next unchecked task
/bt-execute @plan.md T4                      # one task
/bt-execute @plan.md T3-T7                   # a range, in plan order   (T12- = through the end)
/bt-execute @plan.md NEXT:3                  # the next three unchecked tasks
/bt-execute @plan.md ALL                     # every remaining task (resumable)
/bt-execute @plan.md "mind the physics layer"    # a brief shapes HOW, never WHICH task
/bt-execute --strict @plan.md ALL            # adversarial verifier on every task
/bt-execute --auto-pilot @plan.md ALL        # unattended; combine with --strict if wanted
/bt-execute --no-time-limit @plan.md ALL     # turn off the default TIME MATTERS mode
/bt-execute --verbose @plan.md ALL           # a fully written-up dashboard: every task and the After Action Report in depth
```

- Strip `--auto-pilot` / `--strict` / `--verbose` / `--no-time-limit`, and any literal `TIME MATTERS`, first (anywhere in the arguments, never part of the brief). `<plan>` is required — if missing, ask (auto-pilot: say so and end). Never guess a path.
- `[task]` is the token right after the plan, only if it is `T<id>`, `T<a>-T<b>`, `T<a>-`, `NEXT`, `NEXT:<n>` or `ALL` (case-insensitive). Otherwise it is part of the brief, and the task defaults to `NEXT` (`ALL` under auto-pilot). Never ask which task to run.
- A range is a slice of the checklist **in file order** (sub-tasks like `T3.1` between the endpoints included). An unknown id → list the available ids and stop. A reversed range → error; never swap it. Tasks outside the slice are never touched.
- Tasks already `- [x]` are skipped — that is what makes every mode resumable. Nothing left to do → say so and stop. Except in `ALL` / range / `NEXT:<n>` runs, do one task and do not continue to the next.
- **`--auto-pilot` overrides every stop in this skill.** Wherever a rule below says *stop*, *ask* or *tell the user*, an auto-pilot run follows the **Auto-pilot** section instead — read it before the first task.

## Ground rules

- **TIME MATTERS** — on by default; `--no-time-limit` turns it off. Treat the arguments as ending with `TIME MATTERS`: the user is waiting on this run, so finish quickly — follow the *Work fast* rules below to the letter, take the direct route to each task's Acceptance, and do not re-read what you already have. Begin every implementer and verifier prompt with `TIME MATTERS.` Print `⏱️ [bt-execute] TIME MATTERS` at the start (`--no-time-limit`: print `⏱️ [bt-execute] No time limit`, and do not add it). Speed never relaxes tests, the independent verifier, live checks, or "tick only on PASS".
- **Scope.** Implement only the selected task(s). No "while I'm here" work on other tasks. Ambiguous, or blocked by an unfinished task → stop and tell the user *(auto-pilot: decide and log it)*.
- **Open the run before anything else.** The first actions of every run — before reading docs, reading code, checking the repo or any other pre-flight work — are, in order: take the clock; append the `⏱ Run <n> start` line to the run log; sync the dashboard with the plan and set `status: "in-progress"` (*Run start* under *Feature folder and dashboard*); write the live file (`role: "orchestrator"`, `title: "Starting run <n> — <what you are checking first>"`); and launch the watchdog in the background (*Never let the dashboard go stale*). From then on the pre-flight work is narrated in the live file like any other step. Until the run is opened the dashboard still shows the last run's end state — a user who restarts a run and refreshes must see it running within a minute, not after the pre-flight is over.
- **Read the docs once.** For Babylon work, if you have not read the Agent Reference this session, read it once — https://raw.githubusercontent.com/babylontoolkit/agent/main/reference.md — plus only the sub-documents the plan's tasks need, searching a large one for the part you need rather than reading it whole. It is the authority for conventions and API. Cannot be read → stop and tell the user *(auto-pilot: retry 3×, then continue on what you know and log it)*. Read the plan's checklist and the parts of `SPEC.md` the tasks touch; re-read after a context compaction.
- **SPEC.md** constrains how you build. If the code and SPEC.md disagree, stop and tell the user *(auto-pilot: decide which is right, fix SPEC.md in the same task, log it)*. When a task changes architecture, a system, a convention or a dependency, SPEC.md must end up matching — normally the plan's final `Update SPEC.md` task; if the plan has none, do it anyway; a new dependency is recorded in SPEC.md by the task that introduces it. Follow SPEC.md's "How to update this spec". **Write the product, never the procedure** — no capture protocols, tool lists, ledgers or gates: recorded there, they become a bar every later feature must clear.
- **Say what you are doing** — one short line at each task and phase boundary, and before anything slow.
- **Clock every run** — auto-pilot or not, so bt-plan's time estimates can be recalibrated from real runs. Take every time from the shell (`date '+%Y-%m-%d %H:%M %Z'`, local time), never from memory, the conversation or a tool result's UTC timestamp. Append to the run log `documents/<slug>_autopilot.md` beside the plan (a legacy plan keeps its existing `<plan-basename>_autopilot.md`; an interactive run writes only these lines and its task lines):
  - Run start: `⏱ Run <n> start <date time> · queue T<a>–T<b> (<k> tasks) · plan estimate <the plan's Total line, or none> · flags <auto-pilot / strict / interactive>`
  - Each phase — read the clock when the implementer launches, when each verifier launches, and at the tick — once its tasks are ticked or deferred: `⏱ Phase <N> (T<a>–T<b>): <HH:MM>→<HH:MM> · <m> min · build <m> · verify <m> · fix <m> (<rounds> rounds)`. Time spent waiting on the user (a question, a permission prompt) is logged as `· waited <m>` and left out of `<m> min`.
  - Each task line ends `· done <HH:MM>`.
  - Run end: `⏱ Run <n> end <date time> · <done>/<k> tasks · active <h m> · <min> min/task · waited <m>`.
- **Subagents:** running this skill is the user's request to use them. Use whatever subagent tool your host provides (its name varies by host — e.g. `Agent` or `Task`); if there is none, work inline, self-verify with the same checklist, and say so.

## The loop

Work in **phases**: a `### Phase N` group in the plan, or — if the plan has none — up to 3 consecutive tasks (a `live` task, the `Update SPEC.md` task and the last task each close a group). A single task or `NEXT` is a phase of one. Under `--strict` every task is its own phase.

1. **Build** each task in the phase, in order, **following the Agent Reference's Coding Practices — ENFORCED** (clean, professional TypeScript or JavaScript in the project's own language; meaningful full-word names, never one- or two-letter names or obfuscation; well-structured, readable, maintainable code for human developers; meaningful JSDoc on every class, function, method and public member — always written, never a reason to fail a task), **with its tests**: the cases the plan's `Tests:` names (or, with none, meaningful cases for its Acceptance and edge cases), in the feature folder's `tests/` (`.agents/specs/<slug>/tests/` — never a root `tests/` folder), using the repo's test runner and style. Get them green — fix the code, not the test, unless the test is wrong. No testable surface (config, docs, assets) → say so. A task with visible output also **saves its progression snapshots** as it builds (*Snapshots tell the story*, below). The implementer keeps the **dashboard current task by task** — the live file at every step, the task's entry at start and the moment it is built — so the user never waits for the phase to end to see progress. Boxes stay unticked.
2. **Verify** the phase with a fresh **independent verifier** subagent (charter below), giving it the list of files changed. It returns PASS/FAIL per task, with evidence, and marks each task `verifying` on the dashboard (and the live file) as it checks it.
3. **Tick** `- [ ]` → `- [x]` for every task that passed, immediately — except a task that depends on one that failed in the same phase, which waits for it. Never tick partial, skipped or unverified work. Mark each ticked task `done` on the dashboard as you tick it, then write the phase's dashboard entry before its commit.
4. **Fix loop** for a task that failed: fix the code in the context that wrote it; re-run its tests; re-verify with a **fresh** verifier given only the failed items and the evidence (`--strict`: the whole task). A records-only slip (a stale number or note) is fixed directly and re-checked by you. 3 attempts (`--strict`: 5), each changing something material; stop early if two attempts fail the same way with no new idea. Still failing → leave it unticked, stop and report *(auto-pilot: defer and continue)*.
5. **Report:** tasks done (for `ALL` / ranges: the range asked for, completed/total, and whether the plan is now finished; if fewer than `n` tasks remained for `NEXT:<n>`, say so), files changed, tests run (`tests: 4 passed (implementer) · verifier-checked`), verifier result (`verified (independent subagent)` or `verified (self)`), the dashboard path (`.agents/specs/<slug>/dashboard.html` — open it in a browser), and the next task id — for reference only.

**The verifier is told:** *"Confirm each task's Acceptance is genuinely met and run its `Verify` commands against the stated expected output. Re-run the tests and the relevant suite once; check they really cover the Acceptance and named edge cases and could fail — missing or vacuous tests are a FAIL. Read the diff for real defects: logic errors, broken callers, unhandled edge cases the plan names, a documented behavior dropped or inverted, a sibling-skill template re-implemented instead of copied. Check every code file the task created or changed against the Agent Reference's Coding Practices — ENFORCED: clean, professional TypeScript or JavaScript in the language the project already uses (never converted to the other unasked); strict types with no needless `any` in TypeScript; meaningful full-word names for every class, method, property, variable and parameter (one- or two-letter names, cryptic abbreviations and code-golf tricks are violations, except the allowed loop counters, axis/`uv` names and toolkit aliases, and names that bind to exported data); no dead code, unused imports or leftover `console.log`; well-structured code a developer new to the project can read and maintain. Any violation is a FAIL for that task — quote the offending lines. JSDoc is never a FAIL: missing, thin or stale JSDoc (including JavaScript type tags) never fails a test, a verification or an Acceptance item — list it under a separate non-blocking `JSDoc notes` heading. For any task whose correctness shows only at runtime — rendering, UI, interaction, Unity↔Babylon parity — check it live in the browser (and Unity where relevant) whether or not the plan marks it `live`, and do the plan's final end-to-end check live: look at the running result, beside the reference image when there is one, and judge it as a user would; passing unit tests never substitute. Do all of a phase's live checks in one session on the already-running dev server, and re-export from Unity only if the phase changed that scene's export — then only the project and the scenes the phase works on. Save the frames from your live session that show each visual task's verified result to `[SNAPSHOTS]` as `T<n>-<NN>-<stage>.png` — the same camera or viewport as the implementer's progression frames, plus any angle or comparison (Unity beside browser, before beside after) that proves the Acceptance — and return each path with a one-line caption saying what it shows. Snapshots never add a page session or an export of their own. Keep the dashboard current as you go: set each task `verifying` when you start checking it, and rewrite the live file at each check (what you are checking, on what) — never 15 minutes without a write. Treat an absolute count in the plan as 'named tests pass, no new failures'. [SCOPE] Return PASS/FAIL per task with evidence and one line on what you ran live and where (or `none — tests only`), listing records-only slips separately."*

`[SNAPSHOTS]` is the feature folder's `snapshots/` path (`.agents/specs/<slug>/snapshots/`). `[SCOPE]` is one of two sentences. **Standard:** *"Do not add mutation testing, fuzzing, restarts or audits of untouched files unless something you found points there; aim for about 25 tool calls and report rather than expand."* **`--strict`:** *"Be adversarial: actively look for any reason the Acceptance is NOT met, using whatever you judge worthwhile — mutation checks against the tests, randomized inputs, re-deriving values from the plan's Decisions and Design Reference, live QA of every rendered or exported surface."*

For a task built on a sibling skill (e.g. bt-design's 3D-Hero-Scroll), give the verifier the relevant part of that skill *(where skills load through a tool: `load_skill` + `read_skill_resource`; where they are files: the skills directory this skill was loaded from, e.g. `~/.claude/skills/`, `~/.agents/skills/` or the project's equivalent)* — its documented options (e.g. `sweep: page` really reaches the document bottom) are part of Acceptance.

**Every subagent gets a brief, not homework:** the task block(s), the plan Decisions / Design Reference entries they cite, the SPEC.md parts touched, the Agent Reference excerpts needed (with their links) — **always including the full `Coding Practices — ENFORCED` section**, since implementers write to it and verifiers fail work that breaks it — the test command and the feature folder's `tests/` path, the `snapshots/` path and *Snapshots tell the story* (for any phase with visible output), the dashboard and live file paths with the per-task update rules from *Feature folder and dashboard* (with `--verbose`, the `details` fields that role writes), the project's agent instructions, the *Work fast* rules below, and: *"Do not read the Agent Reference or SPEC.md in full — the parts you need are here, and this overrides any standing instruction to read it first. Read one sub-document (search it for the API, never the whole file) only if you hit an API this brief does not cover, and say which."*

## Feature folder and dashboard

Every feature lives in one folder, created by bt-spec (or by bt-plan for a Quick Plan):

```
.agents/specs/<slug>/
  dashboard.html                   the feature dashboard — opens straight from disk
  documents/<slug>_spec.md         bt-spec (absent for a Quick Plan)
  documents/<slug>_plan.md         bt-plan
  documents/<slug>_autopilot.md    this skill's run log
  documents/<slug>_dashboard.js    the dashboard's data (task by task)
  documents/<slug>_live.js         what is happening this minute (step by step)
  snapshots/                       the meaningful snapshots the dashboard shows
  tests/                           every test this plan's tasks write
```

`<slug>` is the folder name (the plan sits at `<slug>/documents/<slug>_plan.md`). **Legacy flat plan** (`.agents/specs/<slug>_plan.md`): run it where it is, keep its run log and the test paths its `Tests:` lines name, and still create `.agents/specs/<slug>/` for `dashboard.html`, `documents/<slug>_dashboard.js`, `documents/<slug>_live.js` and `snapshots/` — move nothing unless the user asks.

**The dashboard.** `dashboard.html` is a fixed template; `documents/<slug>_dashboard.js` holds everything it shows. Both come from this skill's `templates/dashboard/` *(where skills load through a tool: `load_skill` + `read_skill_resource`; where they are files: the skills directory this skill was loaded from)*: `dashboard.html` copied with `{{slug}}` replaced — never otherwise edited — and the starter data `dashboard.template.js`. A third file, `documents/<slug>_live.js` (from `live.template.js`), carries what is happening this minute. **`data-schema.md` documents every field and the update recipe — read it once per run and put the parts a role writes into its brief.** bt-plan writes all three in the `planned` state; if any is missing, create it now from the plan.

**Update per task, not per phase — the user watches this page instead of asking "what are you doing?"** Whoever is doing the work writes: the implementer while it builds, the verifier while it checks, you (the orchestrator) between them. Only one agent works at a time in this loop, so writes never collide; if you ever run subagents in parallel, they report back and you write. Every implementer and verifier brief carries the helper's exact command lines with the paths filled in, and these rules. Every timestamp comes from the local clock (the helper takes it for you).

**Never let the dashboard go stale — three guards, because an agent deep in a long task forgets to write:**

1. **The watchdog.** At run start, launch `node <skills>/bt-execute/scripts/dashboard.mjs watch <feature-folder> --watch <your scratch folder>` in the background (add `--watch` for any other folder where the work leaves files — exports, logs, captures). Every minute it checks the live file: after 10 quiet minutes it writes a heartbeat naming the latest file that changed ("still working — latest activity: t19/gp3.log at 21:48"); after 30 minutes with no file change either it says the run may be stalled; and if the live file still names a finished task while another is in progress, it points it at the active task. It exits by itself when the status leaves `in-progress`. A heartbeat is a safety net, not a substitute — the agents' own writes say what is actually happening.
2. **Hand-off writes.** Before you launch any implementer or verifier, set its task(s) `in-progress` (implementer) or `verifying` (verifier) and point the live file at it (`--task T19 --role implementer --activity "Implementer started on T19 — <its first step>" --reset`); when it returns, write what it reported. The live file must never still name the previous task while a new one is being worked on.
3. **Long commands are narrated.** Before any command that may run more than a few minutes (a full test chain, an export or bake, a multi-race or multi-scene browser run), write a step saying what it is and roughly how long it takes; run it in the background where the host allows, and write a step at each milestone its output shows ("race 2 of 4 reached results"). A long run is exactly when the user is watching.

- **The live file — at every meaningful step.** Rewrite `documents/<slug>_live.js` whole (it is small) when a task starts, at each milestone inside it, before anything slow (a build, an export, a bake, a capture, a test run), at each fix attempt, at the hand-over to the verifier and while it checks each task, and at the commit: the phase, the task, the role, one plain-language sentence on what is happening now, and the task's step log. Never let it go 15 minutes without a write during active work — the page flags a 20-minute silence. Between tasks, `task: ""` and a `title` (`Verifying phase 2`, `Committing phase 2`).
- **The dashboard data — at every task boundary:** a task becomes `in-progress` when it starts; `built` the moment it is built and its tests are green — with its summary of what was actually done (and anything surprising), files, tests and snapshots filled in **right then**, not at the phase end; `verifying` while the verifier checks it; `done` when it passes (verifier result, attempts, commit, done time, its `DECISION` lines, and `checkedLive` — one line on what the verifier ran live and where, for every task it checked in the browser or Unity whatever the plan's verify level, `""` when tests alone proved it); back to `in-progress` with `attempts` + 1 on a FAIL. Each change also adds an `activity` line and refreshes `updatedAt`.
- **Every write goes through this skill's `scripts/dashboard.mjs` — never hand-edited.** Each data file is one `window.… =` prefix and one strict-JSON value (the prefix only lets a page opened from disk load it); the helper parses it, changes it, checks the shapes and writes it back atomically, so the page never sees a half-written or malformed file. Use it, not a one-off script of your own: `node <skills>/bt-execute/scripts/dashboard.mjs live <feature-folder> --task T7 --role implementer --activity "…" --step "…"` · `task <feature-folder> T7 --set '{"status":"built","summary":"…"}'` · `activity <feature-folder> "…"` · `status <feature-folder> in-progress` · `check <feature-folder>` (all options in the script's header). Only where Node cannot run, fall back to the parse-and-write-back recipe in `data-schema.md`. Keep each field its documented shape too — a list stays a list (`updates`, `snapshots`, `files`, `decisions`, `notes` …: append, never assign a string); a helper script you give subagents checks the shapes before it writes.

On top of the per-task updates:

- **Run start — the first thing the run does** (*Open the run before anything else*): **refresh `dashboard.html`** — copy it again from the template with `{{slug}}` replaced (it is never edited, so this is always safe, and it is how layout fixes reach dashboards created by older versions); then **sync the dashboard with the plan file** — re-read its checklist and add any phase or task (including sub-tasks like `T3.1`) the dashboard lacks, in plan order, as `pending`, with an `updates` note on it (`Added to the plan after <the plan was complete / phase 2 ran> — <why, if the plan says>`); a task the plan no longer has is removed with an `activity` line saying so. Then `status: "in-progress"`, `runs` + 1, the run-log document link, an `activity` line, the first live-file write, and the watchdog launched in the background. In a git repository, check `.gitignore` has `.agents/specs/*/documents/*_live.js` and append it once if not — the live file is never staged or committed; `<slug>_dashboard.js` and `snapshots/` are.
- **Each phase, after its ticks and before its commit:** the phase's status, times and minutes (from its `⏱` line), its verifier result and a two-or-three-sentence summary of what it delivered; the phase-level snapshots (a progression spanning several tasks — below); `decisions`; `activeTime` — the plan's total across **every run so far** (each finished run's `active` from its `⏱ Run <n> end` line, plus this run's so far), never this run alone; an `activity` line; and a current "so far" `outcome` headline.
- **A deferral:** the task's `status: "deferred"` and `deferredReason`, an `activity` line.
- **Run end — the After Action Report.** **decide the status by re-reading the plan file's checkboxes, never from memory:** `complete` when every task in the plan is `- [x]`; `incomplete` when every task is either ticked or marked ⏭️ DEFERRED; otherwise `paused` (the run covered only a slice, or tasks were added). The page refuses a `complete` it can see is false — it shows the plan as paused with a warning — but the plan file is the authority; never leave `in-progress` behind, because the status picks the page's top slot: `in-progress` shows *Current run activity* (the live file and the milestones), any other run-ended status shows the After Action Report in its place. Write `followUps` for a human, and `afterAction` — the whole plan's execution, start to finish: a one-sentence headline of what the plan delivered; two to four paragraphs on what was built, how it was proven and what surprised; highlights; and **one before/after for the plan as a whole** (`comparison`) — the plan-wide "before" frame beside a final "after" taken now from the same camera or viewport (the end-to-end check's session supplies it). Add the plan's key progression to `afterAction.snapshots` if one tells the story better than any single phase. Write `afterAction.testing` on every run, not only `--verbose`: run every test suite the plan touched **once more, in full, at run end** and record each as a `suites` entry (name, command, passed, failed, how many tests this plan added, and a `note` for any failure that pre-dates the plan) — never add up the tasks' counts, which re-count the same suite once per task; a `summary` of how the plan was tested (unit tests, the verifier's re-runs, what was checked live and on what, the end-to-end check); and `gaps` — what no test or live check covers. The page builds the task-by-task table and the list of test cases from the tasks. The figures (tasks, tests, retries, time) are computed by the page — never type them in. A run that ends before the plan is finished writes it too; the page marks it *Interim* while `paused`, and the next run revises it with an `updates` entry. **A reopened plan** (tasks added after it was complete) works the same way: the run that finishes the added tasks rewrites the After Action Report to cover them, notes the change in its `updates` (`Revised — T7 added after completion: <why>`), and retakes the plan-wide "after" from the same camera so the comparison shows the plan as it now stands.
- **`--verbose` — the same work, written up in depth.** It changes what is written, never what is done: tests, the verifier, live checks and snapshot captures are exactly as without it, and TIME MATTERS still holds (the extra cost is writing, not checking). Set `detail: "verbose"` at run start. Each task gets a `details` write-up (fields in `data-schema.md`), filled in by whoever has the facts, at the same per-task moments as everything else:
  - **the implementer, when the task is built:** `approach` (how it was built, how the pieces fit together, why this way and not the alternatives it weighed); `changes` — every file touched, with what changed in it and why; `testCases` — every named case with its expected and actual result, the result leading with `PASS` or `FAIL` (`"PASS — 0→74 km/h on held W"`); `problems` — each failed attempt or dead end, with what failed, the root cause and the fix; `notes` for a future maintainer; `timing.build`;
  - **the verifier, while it checks:** `acceptance` — every Acceptance item with its verdict and the evidence it rests on (command output, the screenshot, the line read); `liveCheck` — what it looked at, on which engine, at what resolution, and how it judged it; `timing.verify`;
  - **you, at the tick and in the fix loop:** each fix round added to `problems`, `timing.fix`, and snapshot captions that say what to notice, not just what is shown.

  At run end the After Action Report adds `sections`, one card each where it applies: **Architecture** (what now exists and how it connects), **Phase by phase**, **Problems and resolutions**, **Deviations from the plan** (and why), **Known limitations**, **Lessons learned**, **Estimate vs actual** (per phase, from the `⏱` lines), **Recommended next steps**. Plain language a new developer can follow, concrete over vague — name the files, classes, numbers and screenshots. A later run without `--verbose` keeps everything a verbose run wrote and never thins it; `detail` stays `verbose`.
- **Updated notifications.** Never silently rewrite an earlier part of the dashboard. When later work changes an earlier result — a figure corrected, a decision reversed, a reopened task, a snapshot superseded by a better one — change it and append `{ at, by: "T<n>", note }` to that entry's `updates`. The page badges it **Updated** and lists it under *Updates and revisions*. A superseded snapshot stays; add the new one beside it.
- The dashboard is a record, never a gate: a dashboard slip never fails or blocks a task. At run end, leave the live file's last entry saying the run finished (the page hides it once the status is no longer `in-progress`).

### Snapshots tell the story

The snapshots are how a human sees what was built, so choose them for meaning, not coverage. Never just one before and one after per task: show **how the work came together**.

- **Progressions first.** For a task with visible output, capture a frame each time a meaningful layer of the work lands, from the **same camera or viewport** every time so the frames line up, and caption each with what that stage added. A terrain: heightmap → splat textures → road network → trees → foliage → baked lighting. A UI: layout → styling → states → motion. A shader: base colour → each lighting term → final. A level: blockout → props → lighting → post. A progression can span several tasks; record it on the phase, with each frame's `task`.
- **Then whatever proves the point.** A comparison when a change is best seen side by side (a fix, the state before the phase, Unity beside the browser for parity); a second angle when one view hides it (overview, ground level, close detail); a still when one image proves one thing.
- **As many frames as the build has meaningful stages** — usually 3–8 for a visual task, none for a task with nothing to see. No near-duplicates, no frame per iteration, and a failed attempt only when it explains a decision (say so in the caption).
- **Who takes them.** At the start of the first run, before T1 changes anything, take the **plan-wide "before"** (`snapshots/plan-before.png`) from the camera or viewport that will best show the finished feature — the starting state, even if that is an empty scene or the old page; skip it only when the plan has nothing to see. The implementer saves a "before" frame before the first change of a visual phase, and saves milestone frames while it builds — it is already capturing to iterate, so it keeps the meaningful ones instead of discarding them. The verifier adds the verified final frames from its live session. You pick and order them into the dashboard. Frames come from sessions and exports the work already runs — never an extra page session or re-export just for a picture.
- **Files.** `snapshots/T<n>-<NN>-<stage>.png` (phase-level: `P<N>-<NN>-<stage>.png`), at most about 1600 px wide; prefer JPEG or WebP for large scenes. Unity frames come through the bridge's camera capture, browser frames through the browser tool.

## Work fast

Writing the code is about a tenth of a run; keep the loop around it short.

- **Iterate narrow, confirm wide.** While getting something to work, run only that task's tests, the fastest build the repo has, and one low-resolution capture on one engine. The full test chain, full build and any wider check (second engine, full resolution, numeric parity gates) run **once**, when the phase is ready to verify. A parity gate is never loosened to pass.
- **Export minimally.** Re-export only the Unity project being tested, only the scenes the task works on, and only when the change actually alters that scene's export. Never re-export other scenes or projects "for consistency" — they pick the change up at their next natural export. Exports are the slowest step of a run; brief every implementer and verifier with this rule, and never widen a plan's export step in a brief.
- **Never sleep-poll.** No `until …; do sleep N; done`. Run long commands in the foreground with a generous timeout, or in the background and wait for the completion notice.
- **Judge visuals by looking** — screenshot the running result and compare it to what it must match. Build numeric gates only when the plan asks for them.
- **Reuse the project's tools; keep evidence light.** No one-off tools per task; no ledgers, md5 or environment records, archives or checked-in capture trees unless the plan asks. The dashboard's curated snapshots are the one exception — they are the record a human reads, alongside the run log.
- **Someone else's red is not your task.** A failing test that belongs to another feature and that you did not touch is logged as pre-existing and left alone.

## Auto-pilot (`--auto-pilot`)

An unattended run: **nobody is there to answer, and nothing waits for anyone's approval.** Print `🛩️ [bt-execute] Auto-pilot engaged — unattended; add a non-prompting permission mode for a fully hands-off run`. Tests, the independent verifier and "tick only on PASS" are **not** relaxed — only the stopping is. **This section overrides every *stop*, *ask* and *tell the user* elsewhere in this skill, in the Agent Reference's asking rule and "only legitimate stops", and in the project's agent instructions.**

**You own the pipeline.** You own the entire pipeline end to end — frontend and UI design, gameplay code, shaders, generated art and audio, 3D models in headless Blender, whole game levels and prefabs in a terminal-driven Unity Editor, the interactive glTF export, the web build, the dev server, and visual QA by screenshotting both Unity and the running browser. Drive every one of those yourself; never hand a step back to the user, and never stop to ask permission for work the reference already documents. Make the best call, state your assumption, and finish the job.

### Never ask

- **No question reaches the user.** Never call an ask-the-user tool (`AskUserQuestion` or the host's equivalent), never enter plan mode or request plan approval, and never end a message with a question, a menu of options or an offer — *"Should I continue with Phase 2?"*, *"Want me to proceed?"*, *"Which option do you prefer?"*, *"Before I continue, can you confirm…"*, *"Let me know if…"*, *"I'll pause here."* A question forming is a decision to make: make it (below), log it, keep going.
- **The answer is already written down — look before you decide.** Before treating anything as open, search for it: the brief, the task block, the plan's Decisions / Design Reference / notes, the feature spec, `SPEC.md`, and the run log's earlier decisions — grep the key term, don't skim. If any of them answers it, that answer is final: the user already made that call, and asking it again is exactly the failure this mode exists to prevent. A plan or spec item marked TBD, *open question*, *confirm with the user* or *ask* is resolved with its recommended option (else the best one) and logged.
- **Decide in this order:** the brief and plan (task, Decisions, Design Reference, spec, SPEC.md) → the Agent Reference and its sub-documents → the codebase's existing patterns → what a senior Babylon Toolkit developer would ship: the Unity → interactive glTF → BabylonJS script-component workflow, simplest thing that meets Acceptance, reversible over clever. The chain always ends in an answer — a decision is never escalated. Log each one in one line: `DECISION T7: <choice> — <source or reason>`.
- **The Agent Reference's four "ask" cases are decided too, never asked:** creative or product direction → infer it from the spec, plan, reference images and existing project; an architectural fork → the plan's Decisions, else the more reversible branch; destructive acts on the user's own work, or spending money / acting outward that the plan does not call for → skip only that step, defer it with the reason (see *Safety*), and keep building everything else.
- **Subagents:** put this in every implementer and verifier prompt, right after `TIME MATTERS.`: *"AUTO-PILOT: unattended run. You own the entire pipeline — code, UI, shaders, generated assets, Blender, Unity, export, build, dev server and visual QA at both ends. Never ask a question or hand a step back; the answer is in this brief, the plan, the Agent Reference or the codebase. Decide, state each assumption in one line, and always return a result."* A subagent that returns a question, "needs input" or a half-finished result anyway: answer it from the plan yourself and send it back (or relaunch it) — never relay it to the user.

### Never stop

- **The run ends only when the work queue is empty** — every task in it `- [x]` or deferred. The queue is the range asked for (`T3-T7`, `T12-`, `NEXT:<n>`), or every remaining task for `ALL` or no task id. Before ending, re-read the plan: an unticked, undeferred task in the queue means you are not done.
- **Ending your turn is stopping.** A finished task or phase, a commit, a milestone worth reporting, a long session, many tasks done, a compaction, a tool error, an ambiguity, a hard external blocker — none of these ends the turn. Narrate the boundary in one console line and start the next phase in the same turn. The only mid-queue turn end is waiting on a background job or subagent that will notify you, and that message is one status line (`waiting on T9 verifier`), never a question or a summary inviting a reply.
- **The only early exits — exactly four:** the plan file is missing; a range endpoint does not exist or is reversed (a typo the user must fix — say so and end); the brief names a stop point (`stop after T5`, `stop before the Unity tasks`) — stop there; the user tells you to stop during the run. Nothing else. An Agent Reference that cannot be read → retry 3×, then continue on what you know and log it. A missing Pro license, an account, a credential or a sign-in only the user has → defer the tasks that need it and keep running every task that does not.
- After a compaction, re-read the plan and the run log and continue from the first unticked, undeferred task.

### Keep moving

- **Blocked by an unfinished task:** if it was deferred this run and the fix is now apparent, re-attempt it; otherwise do the minimum of it needed to unblock, log the scope expansion; never tick a task outside the work queue.
- **Errors:** read the error, fix the cause, retry; transient ones (network, port in use, lock file, editor still compiling) → wait and retry up to 3×. **Tools down** (Unity, Blender, dev server, browser): restart or install them through their CLI and retry; genuinely unavailable → defer the task.
- **Permission denied:** a tool call the host's permission mode refuses is respected, never worked around — log it, defer only that step with `permission denied: <action>`, and continue with everything else. The README's non-prompting permission mode is how the user avoids these.
- **Defer, don't stall.** A task that cannot pass keeps `- [ ]` and gets ` ⏭️ DEFERRED (auto-pilot): <reason>` appended to its line; continue. A dependent that cannot proceed is deferred `blocked by T<n>`. When the queue is done, make one more pass over the deferred tasks; one that now passes loses the marker and gets its tick.
- **Safety.** Never push, force-push, deploy, publish, spend money, or delete/overwrite anything outside the plan's scope unless the plan explicitly says so — defer that step instead. Asset generation the plan or spec explicitly calls for (images, textures, audio, video, 3D through the documented generation tools) is in scope: do it. Never `git init`.
- **Checkpoints.** In a git repo, commit after each phase's boxes are ticked: `T<n>: <title> (auto-pilot)` (or `T<a>–T<b>: …`). On the default branch, first switch to `autopilot/<plan-basename>`. Uncommitted changes that are not yours → leave them untouched and stage only the paths this run changed; never ask about them.
- **Context.** Implement each phase in a fresh implementer subagent (it builds and tests; keep it for that phase's fix loop), so you only orchestrate: read plan → implementer → verifier → tick → commit → log → next phase. The plan's checkboxes and the run log are the only state — re-read them at each phase boundary and after a compaction.
- **Run log** — `documents/<slug>_autopilot.md` beside the plan, appended per run: the `⏱` lines from *Clock every run* and completed/total; one line per task (outcome, attempts, tests, verifier, files, commit, done time); one line per decision; deferred tasks with what a human should look at first. Narrate the same boundaries to the console: `▶ [auto-pilot] T12/50 — <title>`, `✅ … verified`, `⏭️ … deferred — <reason>`.
- **Exit report** — only once the queue is empty: tasks completed, completed/total, deferred tasks with reasons, decisions logged and the run-log path, the dashboard path, branch and last commit, whether the plan is done. It states results; it asks nothing. Re-running the same command resumes and re-attempts deferred tasks.
