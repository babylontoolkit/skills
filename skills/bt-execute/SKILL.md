Run tasks from a plan: build each with its tests, have an independent verifier check it once, tick only on PASS, keep the feature's dashboard current. Follow the project's agent instructions (AGENTS.md / CLAUDE.md / .github/copilot-instructions.md). The user's message after the skill name is the `arguments`.

```
/bt-execute [--auto-pilot] [--strict] [--verbose] [--no-time-limit] <plan> [task] [brief]

/bt-execute @.agents/specs/<slug>/documents/<slug>_plan.md ALL   # every remaining task (resumable)
/bt-execute @plan.md                    # NEXT: the next unchecked task
/bt-execute @plan.md T4                 # one task  ·  T3-T7 a range  ·  T12- to the end  ·  NEXT:3
/bt-execute @plan.md "mind the physics layer"   # a brief shapes HOW, never WHICH task
```

- `--auto-pilot`: unattended. `--strict`: an adversarial verifier on every task. `--verbose`: an in-depth dashboard. `--no-time-limit`: TIME MATTERS off. Strip these and any literal `TIME MATTERS` first. `<plan>` is required — missing → ask *(auto-pilot: say so, end)*; never guess a path.
- `[task]` is the token after the plan only if it is `T<id>`, `T<a>-T<b>`, `T<a>-`, `NEXT`, `NEXT:<n>` or `ALL` (any case); otherwise it is brief, and the task is `NEXT` (`ALL` under auto-pilot). Never ask which.
- A range is a checklist slice in file order, sub-tasks (`T3.1`) included. Unknown id → list the ids, stop; reversed → error, never swap. Nothing outside it is touched.
- `- [x]` tasks are skipped, so every mode resumes; nothing left → say so, stop. Only `ALL`, ranges and `NEXT:<n>` run past one task.
- **`--auto-pilot` overrides every *stop*, *ask* and *tell the user* below** — read **Auto-pilot** first.

## Ground rules

- **TIME MATTERS** (default): follow *Work fast*, take the direct route, never re-read. Print `⏱️ [bt-execute] TIME MATTERS` (or `⏱️ [bt-execute] No time limit`) and start every subagent prompt with `TIME MATTERS.` unless it is off. Speed never relaxes tests, the verifier, live checks or "tick only on PASS".
- **Never commit** — no git commit, stage, stash, reset, checkout, push or branch switch, in any mode. Changes stay in the working tree.
- **Snapshots tell the story — ENFORCED.** The dashboard's snapshots are the chronicle of how the plan came together, read long after the run; a row of "No snapshot" loses that record for good. Every visual task leaves its progression on the page *as it is built*, through `dashboard.mjs snapshot` only (*Snapshots tell the story*, below). Speed, TIME MATTERS and `--auto-pilot` never thin it.
- **Scope:** only the selected tasks. Ambiguous, or blocked by an unfinished task → stop and tell the user *(auto-pilot: decide, log it)*.
- **Open the run first** — before docs, code or pre-flight: take the clock, append `⏱ Run <n> start`, do *Run start* and launch the watchdog, so a refreshed dashboard shows the run within a minute.
- **Never let the dashboard go silent — ENFORCED.** *Current run activity* is how the user knows the run is alive; a "no update for 28 min" while work goes on reads as a hung run. Keep the live file current between status changes and run the watchdog behind it (*The live file*, below).
- **Read the docs once:** for Babylon work, the Agent Reference (https://raw.githubusercontent.com/babylontoolkit/agent/main/reference.md) once per session plus only the sub-documents the tasks need, searched — the authority on conventions and API. Unreadable → stop and tell the user *(auto-pilot: retry 3×, carry on, log it)*. Read the checklist and the `SPEC.md` parts the tasks touch; re-read after a compaction.
- **SPEC.md** constrains the build. It disagrees with the code → stop and tell the user *(auto-pilot: decide, fix SPEC.md in that task, log it)*. Changes to architecture, systems, conventions or dependencies leave SPEC.md matching (the plan's `Update SPEC.md` task, or anyway), per its "How to update this spec". **Write the product, never the procedure** — no capture protocols, tool lists, ledgers or gates, which would bind every later feature.
- **Say what you are doing** in one line at each boundary.
- **Clock every run**, any mode — bt-plan re-fits its estimates from it. Shell times only (`date '+%Y-%m-%d %H:%M %Z'`), appended to `documents/<slug>_autopilot.md` (legacy plans: `<plan-basename>_autopilot.md`; interactive runs write only these and task lines):
  - `⏱ Run <n> start <date time> · queue T<a>–T<b> (<k> tasks) · plan estimate <the plan's Total line, or none> · flags <auto-pilot / strict / interactive>`
  - per phase, after its ticks (clock read at build start, verifier launch, tick): `⏱ Phase <N> (T<a>–T<b>): <HH:MM>→<HH:MM> · <m> min · build <m> · verify <m> · fix <m> (<rounds> rounds)`, plus `· waited <m>` for time waiting on the user, not counted in `<m> min`
  - task lines end `· done <HH:MM>`
  - `⏱ Run <n> end <date time> · <done>/<k> tasks · active <h m> · <min> min/task · waited <m>`
- **Subagents:** this skill is the request to use them (`Agent`, `Task`, …). None → work inline, self-verify with the charter, say so.

## The loop

Work in **phases**: the plan's `### Phase N` groups, else up to 3 consecutive tasks (a `live` task, `Update SPEC.md` and the last task close a group). `--strict` makes every task a phase.

**Who builds:**

- **A queue of 3 tasks or fewer** (a small plan says *Runs inline*): you build them, then one independent verifier checks them all.
- **Tracks** (`Track: <letter>`): one builder subagent per track, all at once, each given its owned files from the plan's *Tracks and owned files* and the *Parallel rules*. A `Track: integration` task is the closing step you run once the phase's tracks are built. The phase verifier starts when all of it is built; the next phase may build meanwhile unless it depends on this one.
- **No tracks:** one builder subagent per phase, tasks in order, kept for its fix loop.

1. **Build** to the Agent Reference's **Coding Practices — ENFORCED** (clean code in the project's language, full-word names, maintainable structure; JSDoc always, never a fail reason) and, for HUDs and overlays, **Game UI Performance — ENFORCED** (per-frame values through refs and one frame loop, never React state, props, a store or per-frame EventBus messages). Write the tests `Tests:` names (else meaningful Acceptance and edge cases) in the feature folder's `tests/`, in the repo's runner and style; get them green — fix the code, not the test, unless the test is wrong; nothing testable → say so. A visual task **saves its progression as it builds** (*Snapshots tell the story*): a "before" frame before its first change, a frame each time a meaningful layer lands, and its built frame, kept from the captures it takes to iterate, from the same camera, and added with `dashboard.mjs snapshot` **before** its `built` write. It checks its own work with **one quick look** (a capture at one viewport, or a scripted probe) and never runs the Acceptance's live proof; that is the verifier's.
2. **Verify** with an **independent verifier** subagent (charter below) given the changed files — one per phase (`--strict`: per task), the only live checker, returning PASS/FAIL per task with evidence.
3. **Tick** each passed task `- [x]` at once, unless it depends on one that failed this phase. Never tick partial, skipped or unverified work.
4. **Fix loop:** write the FAIL first (`task <feature-folder> T<n> --set '{"status":"in-progress","attempts":<n>}'`), so the dashboard shows the fix round instead of a task stuck at `verifying`; the task's builder fixes it and re-runs its tests; then **resume the same verifier** (`SendMessage` or equivalent) with only the failed items and the fix — never a fresh verifier (`--strict`: a fresh adversarial verifier re-checks the whole task). Records-only slips (a stale number or note) you fix and re-check. 3 attempts (`--strict`: 5), each changing something material; stop early when two fail alike with no new idea. Still failing → unticked; stop and report *(auto-pilot: defer, continue)*.
5. **Report:** tasks done (range, completed/total, plan finished?), files changed, tests (`tests: 4 passed (builder) · verifier-checked`), `verified (independent subagent)` or `verified (self)`, the dashboard path, the plan summary path if written, the next task id.

### Parallel rules — in every track builder's brief

- **Files:** edit only your track's files. A file two tracks need (route table, `package.json`, lockfile, shared stylesheet, test list) belongs to one track or to integration. Need another track's file → stop that item and report it; never edit it.
- **Shared processes:** never restart, stop or re-launch a shared dev server, game server or proxy. Use your own DevTools port and scratch folder. Unity or Blender work on one project stays on one track.
- **Builds and installs:** no `npm install` or dependency change while tracks run (one track does it first, or integration). Run only your own type-check and tests; the full build that writes shared output (`dist/`, `*.tsbuildinfo`, kit bundles) runs once, by the orchestrator, after the tracks. A type error in a file you do not own is noted, never fixed.
- **Tests and records:** your tests write only to their own `mkdtemp` folders; write only your own tasks' dashboard entries; no git command that changes the working tree or index.

### The verifier's charter

*"Confirm each task's Acceptance is met and run its `Verify` commands against their expected output. Re-run the tests and the relevant suite once; tests that miss the Acceptance or named edge cases, or could not fail, are a FAIL. Read the diff for real defects: logic errors, broken callers, unhandled named edge cases, documented behavior dropped or inverted, a sibling-skill template re-implemented instead of copied. FAIL a touched code file that breaks Coding Practices — ENFORCED: not in the project's language; needless `any`; one- or two-letter names, cryptic abbreviations or code-golf tricks (loop counters, axis/`uv` names, toolkit aliases and exported-data names excepted); dead code, unused imports, leftover `console.log`; structure a newcomer cannot maintain. FAIL a HUD, overlay or GUI file that breaks Game UI Performance — ENFORCED: a per-frame value (speed, needles, timers, bars) through React state, props, context, a store or a per-frame EventBus post; a setter, `dispatch(` or `EventBus.PostMessage(` inside `requestAnimationFrame`, a frame-loop hook, a render observable or `update()`; `width` / `height` / `top` / `left` / `innerHTML` / SVG geometry written, or layout read, per frame; a Babylon GUI control assigned every frame without a changed-value check; a frame loop on a menu, pause or results screen, splash, preloader or landing page, or doing what CSS could (a 3D or scroll-scrubbed hero that pauses off-screen is fine); a HUD loop writing while hidden or paused; a CSS `transition` on a property the loop writes. Quote the lines. JSDoc is never a FAIL — list gaps under non-blocking `JSDoc notes`. You are the only live checker: check live (browser through `bt-cdp.mjs`, Unity where relevant) every task whose correctness shows only at runtime — rendering, UI, interaction, Unity↔Babylon parity — and the plan's final end-to-end check, judging the running result as a user would, beside any reference image; unit tests never substitute. One session per phase on the running dev server, exporting only as *Work fast* allows. Save the frames from that session that show each visual task's verified result to `[SNAPSHOTS]` as `T<n>-<NN>-<stage>.png`: the same camera or viewport as the builder's progression, plus any angle or comparison (Unity beside browser, before beside after, running beside reference) that proves the Acceptance. Add each to its task with `dashboard.mjs snapshot` and return each path with its one-line caption. Snapshots never add a page session or an export of their own, but inside your session a capture costs seconds, so take it. Set each task `verifying` as you start it, and write the live file (`dashboard.mjs live`) before each slow step — an export, a capture pass across tracks or scenes, a long test run — so it is never 15 minutes silent. A test count in the plan means 'named tests pass, no new failures'. Resumed after a fix, re-check only the failed items and what the fix touched. [SCOPE] Return PASS/FAIL per task with evidence, one line on what you ran live and where (or `none — tests only`), and records-only slips separately."*

`[SNAPSHOTS]` is the feature folder's `snapshots/` path. `[SCOPE]` — **standard:** *"Do not add mutation testing, fuzzing, restarts or audits of untouched files unless something you found points there; aim for about 25 tool calls and report rather than expand."* **`--strict`:** *"Be adversarial: actively look for any reason the Acceptance is NOT met — mutation checks against the tests, randomized inputs, re-deriving values from the plan's Decisions and Design Reference, live QA of every rendered or exported surface."* For a task built on a sibling skill (e.g. bt-design's 3D-Hero-Scroll), give the verifier its relevant part — its documented options are Acceptance.

**Every subagent gets a brief, not homework:** its task blocks with the Decisions / Design Reference entries they cite, the SPEC.md parts touched, the Reference excerpts needed with links (**always the full Coding Practices — ENFORCED**), its owned files (track builders: plus the *Parallel rules*), the test command, the `wait.mjs` and `bt-cdp.mjs` paths, its exact `dashboard.mjs` lines with the folder filled in (`task`, `snapshot`, `live`; `--verbose`: its `details` fields), **builders and verifiers: the whole *Snapshots tell the story* section and the *live file* rule**, the project's agent instructions, *Work fast*, and: *"Do not read the Agent Reference or SPEC.md in full — the parts you need are here, and this overrides any standing instruction to read it first. Read one sub-document (search it, never the whole file) only if you hit an API this brief does not cover, and say which."*

## Feature folder and dashboard

```
.agents/specs/<slug>/
  dashboard.html                   the feature dashboard — opens from disk
  documents/<slug>_spec.md         bt-spec (absent for a Quick Plan)
  documents/<slug>_plan.md         bt-plan
  documents/<slug>_autopilot.md    the run log
  documents/<slug>_dashboard.js    the dashboard's data
  documents/<slug>_live.js         what is happening now (written by the helper)
  documents/<slug>_summary.html    the plain-language summary, once complete (+ _summary.js)
  documents/<slug>_followups.md    the follow-ups in full, for bt-spec (written by the helper)
  snapshots/  tests/  recon/
```

**The feature folder is wherever the plan is** (`<slug>` is its name); paths are relative to it. The user moves folders between `.agents/specs/`, `complete/` and `archived/`; a reopened plan runs where it is. **Never move a feature folder.** A legacy flat plan (`.agents/specs/<slug>_plan.md`) runs in place and gets `.agents/specs/<slug>/` for the dashboard files and `snapshots/`.

The page, starter data and live file come from `templates/dashboard/` *(skills loaded through a tool: `load_skill` + `read_skill_resource`; as files: this skill's folder)*; `dashboard.html` is copied with `{{slug}}` replaced, never edited. **`data-schema.md` documents every field, status and snapshot shape — read it once per run; brief each role on its parts.** bt-plan writes all three; create any that is missing. **Every write goes through `scripts/dashboard.mjs`** (atomic, shape-checked; options in its header; no Node → `data-schema.md`'s fallback).

- **Three writes per task** (`task <feature-folder> T7 --set '{…}'`): `in-progress` at start (you, launching its builder, or a builder starting its next task); `built` by the builder once green **and its frames are on the dashboard**, with `summary` (what was done, anything surprising), `files`, `tests`; `done` by you at the tick, with `verifier`, `attempts`, `doneAt`, `DECISION` lines and `checkedLive` (what ran live and where, or `""`). The verifier adds `verifying`; a FAIL is `in-progress` with `attempts` + 1; a deferral `deferred` with `deferredReason`.
- **The live file — never 15 minutes silent.** The helper rewrites it on every `task` status change, every `snapshot` and every `status` write. Between those, whoever is working writes it: `live <feature-folder> --task T7 --role implementer|verifier|orchestrator --activity "<one plain sentence on what is happening now>" --step "…"`. Write it at each milestone inside a task, **before anything slow** (a build, an export, a bake, a live session, a test run), at each fix attempt, and as the verifier moves to each task, track or scene. Never let it go 15 minutes without a write during active work; the page flags a 20-minute silence.
- **The watchdog is the safety net, never the substitute.** At run start, launch `node <skills>/bt-execute/scripts/dashboard.mjs watch <feature-folder> --watch <the project's source folder> --watch <your scratch folder>` in the background, adding `--watch` for any other folder the work writes (exports, logs, captures). After 10 quiet minutes it writes a heartbeat naming the latest file that changed ("still working — latest activity: snapshots/T2-03-fix.png at 16:42"). After 30 with no file change either, it says the run may be stalled. It exits by itself once the status is no longer `in-progress` (or after 12 hours). A host that cannot run a background process skips it and keeps the live writes tighter.
- **Snapshots are the chronicle — ENFORCED**, added only with `snapshot <feature-folder> <T<n>|P<N>|plan> --src snapshots/… --caption "…"` (`--before … --after …`: comparison; `--frame "src|stage|caption"` repeated: progression; target `comparison` with `--before`/`--after`: the plan-wide before/after), never snapshot JSON. Who takes which frames, and when: *Snapshots tell the story*, below.
- **`check <feature-folder>` is the gate** at every phase boundary and run end; nothing closes while it fails. It catches snapshots that cannot show and skipped deliverables: a missing page or data file, tasks unlike the plan's checklist, a false or summary-less `complete`, a visual task `done` without a snapshot, frames left in `snapshots/` that no entry shows, a ticked task without a verifier result.
- **A record, never a gate on a task.** Never silently rewrite an earlier result: change it and add `{ at, by: "T<n>", note }` to its `updates` (`--note "…" --by T<n>`), badged **Updated**; superseded snapshots stay.

### Snapshots tell the story — ENFORCED

The snapshots are how a human sees what was built and how it came together. Choose them for meaning, not coverage, and never just one before and one after per task: show **the story of the build**.

- **Progressions first.** For a task with visible output, capture a frame each time a meaningful layer of the work lands, from the **same camera or viewport** every time so the frames line up, and caption each with what that stage added. A terrain: heightmap → splat textures → road network → trees → foliage → baked lighting. A UI: layout → styling → states → motion. A shader: base colour → each lighting term → final. A level: blockout → props → lighting → post. A fix: the fault → the fix. A progression can span several tasks; record it on the phase (`P<N>`), each frame's `task` set.
- **Then whatever proves the point.** A comparison when a change is best seen side by side (a fix, the state before the phase, Unity beside the browser for parity); a second angle when one view hides it (overview, ground level, close detail); a still when one image proves one thing.
- **As many frames as the build has meaningful stages:** usually 3–8 for a visual task, none for a task with nothing to see. No near-duplicates and no frame per iteration; a failed attempt only when it explains a decision (say so in the caption).
- **Who takes them.** *You:* before T1 of the first run changes anything, the **plan-wide "before"** (`snapshots/plan-before.png`) from the camera or viewport that will best show the finished feature. That is the starting state, even if it is an empty scene or the old page; skip it only when the plan has nothing to see. At run end, the plan-wide "after" from the same camera. *The builder:* a "before" frame before the first change of a visual task, milestone frames as each layer lands, and its built frame. It is already capturing to iterate, so it keeps the meaningful frames instead of discarding them, and adds them **before** its `built` write. *The verifier:* the verified frames from its live session. *You* pick, order and caption them into the phase's progression, and add any frame a subagent returned without adding.
- **Cheap, never extra.** Frames come from the sessions and exports the work already runs, never an extra page session or re-export just for a picture. Inside a session that is open anyway, a capture costs seconds: take it.
- **The helper holds the line.** `snapshots/` holds only frames worth showing; iteration captures go to scratch. A task cannot move to `built`, `verifying` or `done` while a `snapshots/T<n>-…` frame of its own is on no dashboard entry. A visual task (kind `live`, `game` or `unity`) cannot be `built` with no snapshot at all; `--no-frame "<why>"` is only for a task that truly has nothing to show yet, and the reason lands in the activity log. `check` also fails on a closed phase's unshown `P<N>-…` frames and, once a run has ended, on a `plan-before` the After Action Report does not use. A refusal is fixed by adding the frames, never by moving or deleting them.
- **Files.** `snapshots/T<n>-<NN>-<stage>.png` (phase-level `P<N>-<NN>-<stage>.png`; plan-wide `plan-before` / `plan-after`), at most about 1600 px wide; JPEG or WebP for large scenes. Unity frames come through the bridge's camera capture, browser frames through `bt-cdp.mjs`. Every frame reaches the page only through `dashboard.mjs snapshot`; a subagent that cannot run it returns paths and captions for you to add.

### Run start, phases, run end

- **Run start:** create any missing `.agents/specs/`, `complete/`, `archived/`, `profile/`, `recon/` (each with an empty `.gitkeep`); re-copy `dashboard.html` and an existing `documents/<slug>_summary.html` from their templates; **sync the dashboard with the plan** — add missing phases and tasks in plan order as `pending` with an `updates` note (`Added to the plan after <phase 2 ran / it was complete> — <why>`), remove dropped ones with an `activity` line. Then `status <feature-folder> in-progress`, `runs` + 1, the run-log link, an `activity` line, and **the watchdog launched in the background**; in git, add `.agents/*/*/documents/*_live.js` to `.gitignore` once. Before T1 of the first run changes anything, save `snapshots/plan-before.png`, the plan-wide "before" (*Snapshots tell the story*).
- **Each phase, after its ticks:** status, times and minutes (its `⏱` line), verifier result, a 2–3 sentence summary, the phase's progression (its tasks' frames in build order from one camera, `snapshot P<N> --frame …`) when it spans tasks, `decisions`, `activeTime` (all runs: each `⏱ Run <n> end` line's `active` plus this run's), an `activity` line, a "so far" `outcome`, and `check` passing.
- **Run end — the After Action Report.** Status from **re-reading the checkboxes**: all `- [x]` → `complete`; all ticked or ⏭️ DEFERRED → `incomplete`; else `paused` — never `in-progress`. **Follow-ups:** add each with `followup <feature-folder> --title "<one line>" --detail "…" --source "T<n> <role>" [--file <path>]…` — one per thing a human should look at next (a pre-existing problem the run logged, work outside the plan's scope, a gap no check covered), never a note about what went well. Each carries enough to be specced on its own: what is wrong, the evidence (numbers, where it showed), where to look, what fixing it involves. The helper numbers them `F1`, `F2` …, writes `documents/<slug>_followups.md`, and the dashboard offers a `/bt-spec Fix F<n> from …` command for each, and for any ticked together. A later run revises one with `--id F2 … --note "why"`, never by rewriting it. Then write `afterAction` (fields in `data-schema.md`): headline, body, highlights, **one plan-wide before/after** (`snapshot <feature-folder> comparison --before snapshots/plan-before.png --after snapshots/plan-after.png --caption "…"`), the "after" from the same camera in the final end-to-end session; the key progression in `afterAction.snapshots` if it tells the story best; and every run `afterAction.testing` — each suite the plan touched re-run **once in full** (one `suites` entry each, never summed from tasks), a `summary` and `gaps`. An early end writes it too (*Interim* while `paused`; revised next run with an `updates` entry); finishing a reopened plan rewrites it, notes the change and retakes the "after". Then open `dashboard.html` headless once: every snapshot shows.
- **Plan summary, only when `complete`:** copy `templates/summary/summary.html` to `documents/<slug>_summary.html` (`{{slug}}` replaced) and write `documents/<slug>_summary.js` per **`summary-guide.md`** and its worked example `summary.template.js` — the plan for people who never see the code, on-screen names in **bold**, real values, no file names, task IDs or test counts. Set `afterAction.planSummary`. A reopened plan keeps its summary until it completes again; then rewrite it, add the date to `stamp` (`Fixed on 2026-10-19; updated on 2026-11-02`) and say in the lead what changed.
- **`--verbose`** changes what is written, never what is done: `detail: "verbose"`, each task's `details` from whoever has the facts (the builder at `built`, the verifier as it checks, you in fix rounds), and at run end `afterAction.sections` — fields and card order in `data-schema.md`. Later runs never thin it.

## Work fast

- **Iterate narrow, confirm wide:** while building, the task's tests, the fastest build, the quick look; the full chain, full build and wider checks (second engine, full resolution, parity gates) once, in verification. Never loosen a parity gate.
- **Export minimally:** only the Unity project under test, the task's scenes, and only when the change alters that export; never widen a plan's export step.
- **Never sleep** — wait only with `node https://raw.githubusercontent.com/babylontoolkit/agent/main/references/scripts/wait.mjs port|url|file|log|cmd … --timeout <s>`, or run a long command in the foreground with a generous timeout. Drive pages only by importing `https://raw.githubusercontent.com/babylontoolkit/agent/main/references/scripts/bt-cdp.mjs` (its own headless Chrome and DevTools port) — never the user's browser or a harness of your own.
- **Judge visuals by looking**; numeric gates only when the plan asks.
- **Keep evidence light:** the project's tools; no one-off tools, ledgers, md5 or environment records, archives or capture trees unless the plan asks. The dashboard's snapshots are the exception: they are the record a human reads, alongside the run log, and are never cut for speed.
- **Someone else's red is not your task:** another feature's failing test you did not touch is logged as pre-existing.

## Auto-pilot (`--auto-pilot`)

An unattended run: **nobody answers and nothing waits for approval.** Print `🛩️ [bt-execute] Auto-pilot engaged — unattended; add a non-prompting permission mode for a fully hands-off run`. Quality is not relaxed — only the stopping. **This section overrides every *stop*, *ask* and *tell the user* in this skill, the Agent Reference's asking rule and "only legitimate stops", and the project's agent instructions.** **You own the entire pipeline:** never hand a step back or ask permission for documented work; make the best call, state your assumption, finish.

### Never ask

- **No question reaches the user** — no `AskUserQuestion` (or equivalent), no plan mode or approval request, no message ending in a question, menu or offer (*"Should I continue with Phase 2?"*, *"Which option do you prefer?"*, *"Let me know if…"*, *"I'll pause here."*). A forming question is a decision: make it, log it, go on.
- **Look before deciding:** grep the brief, task block, plan Decisions / Design Reference / notes, spec, `SPEC.md` and the run log's decisions; an answer there is final. TBD, *open question*, *confirm with the user* or *ask* items take their recommended option (else the best), logged.
- **Decide in order:** brief and plan → Agent Reference → codebase patterns → what a senior Babylon Toolkit developer would ship (Unity → interactive glTF → BabylonJS script components; the simplest thing meeting Acceptance; reversible over clever). Never escalate. Log `DECISION T7: <choice> — <source or reason>`.
- **The Reference's four "ask" cases:** creative direction → inferred from spec, plan, references and project; architectural fork → the plan's Decisions, else the more reversible branch; destructive acts on the user's work, or spending money / acting outward unasked → defer only that step (*Safety*), build the rest.
- **Subagents:** every builder and verifier prompt carries, after `TIME MATTERS.`: *"AUTO-PILOT: unattended run. You own the entire pipeline — code, UI, shaders, generated assets, Blender, Unity, export, build, dev server and visual QA at both ends. Never ask a question or hand a step back; the answer is in this brief, the plan, the Agent Reference or the codebase. Decide, state each assumption in one line, and always return a result."* One that returns a question or half a result: answer from the plan and send it back; never relay it.

### Never stop

- **The run ends only when the queue is empty** — each task in it `- [x]` or deferred (the range, or every remaining task for `ALL` / no id); re-read the plan before ending.
- **Ending your turn is stopping.** No boundary, milestone, compaction, error, ambiguity or blocker ends it: one console line, then the next phase. The only mid-queue turn end is waiting on a background job or subagent that will notify you — one status line (`waiting on the phase 2 verifier`), never a question.
- **Exactly four early exits:** the plan file is missing; a range endpoint is unknown or reversed (say so, end); the brief names a stop point (`stop after T5`); the user says stop. An unreadable Reference → retry 3×, carry on, log it. A license, account, credential or sign-in only the user has → defer the tasks that need it, run the rest.
- After a compaction, re-read the plan and run log — the only state — and continue at the first unticked, undeferred task.

### Keep moving

- **Blocked by an unfinished task:** re-attempt it if deferred this run and the fix is now clear; else do the minimum to unblock, log it; never tick outside the queue.
- **Errors:** fix the cause, retry; transient ones (network, port in use, lock file, editor compiling) → `wait.mjs`, retry up to 3×. **Tools down** (Unity, Blender, dev server, browser) → restart or install via their CLI; truly unavailable → defer.
- **Permission denied** is respected, never worked around: log it, defer that step (`permission denied: <action>`), continue.
- **Defer, don't stall:** keep `- [ ]` and append ` ⏭️ DEFERRED (auto-pilot): <reason>`; dependents are deferred `blocked by T<n>`. After the queue, one more pass: a deferred task that now passes loses the marker and is ticked.
- **Safety:** never push, deploy, publish, spend money, or delete/overwrite outside the plan's scope unless it says so — defer instead. Asset generation the plan or spec calls for is in scope. Never `git init`; leave others' uncommitted changes alone, unasked.
- **Run log** per run: the `⏱` lines, completed/total, a line per task (outcome, attempts, tests, verifier, files, done time) and per decision, deferred tasks with where to look first. Console: `▶ [auto-pilot] T12/50 — <title>`, `✅ … verified`, `⏭️ … deferred — <reason>`.
- **Exit report** once the queue is empty: completed/total, deferrals with reasons, decisions and the run-log path, the dashboard path, that all changes are uncommitted, whether the plan is done. It asks nothing; re-running resumes and retries deferrals.
