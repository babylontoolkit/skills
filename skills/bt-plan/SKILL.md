Turn a feature spec into `.agents/specs/<slug>/documents/<slug>_plan.md`: an ordered checklist of tasks that `bt-execute` runs — plus the feature's dashboard (`.agents/specs/<slug>/dashboard.html`) in its planned state, which bt-execute keeps current — live activity while a run is going, an After Action Report once it is over. Follow the project's agent instructions (AGENTS.md / CLAUDE.md / .github/copilot-instructions.md). The user's message after the skill name is the `arguments`.

```
/bt-plan [--heavy] [--parity] [--no-time-limit] <feature-spec> <optional-brief>

/bt-plan @.agents/specs/mute-game-audio/documents/mute-game-audio_spec.md
/bt-plan "add a settings toggle to mute all game audio"     # no spec file → Quick Plan: short interview, creates the feature folder, then plans
/bt-plan Fix F3 from @.agents/specs/<slug>/documents/<slug>_followups.md   # Quick Plan for a finished feature's follow-ups (its dashboard's copy buttons)
/bt-plan --heavy @.agents/specs/<slug>/documents/<slug>_spec.md   # decision-complete plan for a long or cheaper-model run
/bt-plan --heavy --parity @.agents/specs/<slug>/documents/<slug>_spec.md   # numeric parity gates against the reference (slow)
/bt-plan --no-time-limit @.agents/specs/<slug>/documents/<slug>_spec.md   # turn off the default TIME MATTERS mode
```

- `--heavy` — Heavy Plan mode (below). `--parity` — plan numeric parity proof; also on when the spec says `proof: parity`. `--no-time-limit` — turn off TIME MATTERS mode (Ground rules). Strip flags, and any literal `TIME MATTERS`, first; they are never part of the brief.
- Spec file (± brief) → plan from it. **Brief only → Quick Plan.** Neither → ask for a brief. Never guess a path or URL.

## Ground rules

- **TIME MATTERS** — on by default; `--no-time-limit` turns it off. Treat the arguments as ending with `TIME MATTERS`: the user is waiting on this run, so finish quickly — research only what the plan needs, keep subagents few and their questions narrow, and do not re-read what you already have. Begin every subagent prompt with `TIME MATTERS.` Print `⏱️ [bt-plan] TIME MATTERS` at the start (`--no-time-limit`: print `⏱️ [bt-plan] No time limit`, and do not add it). Speed never skips a required step, the Heavy Plan cold-context audit, or anything the plan needs to be complete.
- **Planning only — in every mode.** Research read-only; the only files you write are the plan and the dashboard (`dashboard.html` and its data files) in the feature folder, plus the one `.gitignore` line Step 4 names; the only commands you run are the shell clock and Step 4's dashboard check. Never implement a task, edit source, or run builds/tests — not even a trivial first task. The passing check is the last action; the user runs `bt-execute` separately.
- **Babylon work:** if you have not read the Babylon Toolkit Agent Reference in this session, read it once: https://raw.githubusercontent.com/babylontoolkit/agent/main/reference.md — the authority for conventions and API; read sub-documents only when relevant, and again only if a context compaction made you forget it. If it cannot be read, stop and tell the user — do not guess at the API.
- **Say what you are doing.** Before any step that takes more than a few seconds print one short line — `🔎 [bt-plan] <what> …` — and one when it returns; one line per subagent going out and coming back. A silent run looks like a hang and gets cancelled.
- **Subagents:** running this skill is the user's request to use them where it says so. Use whatever subagent tool your host provides (e.g. `Agent` or `Task`); if there is none, work inline and say so. Tell exploration subagents they need not read the Agent Reference.

## Step 1. Analyze (required before writing)

1. Read the feature spec in full, and `SPEC.md`'s headings, Architecture, Conventions and the systems the feature touches. The plan must conform to SPEC.md — **if it would conflict, stop and tell the user.** Verification procedures described in SPEC.md are tooling you may reuse, not a bar the plan must meet. Note the spec's `spec_impact`, `size` and `proof`.
2. **Start from the spec's `## Research Notes`, and any bt-recon doc it cites (the feature's own `recon/` copies, or `.agents/recon/*_recon.md`) or whose scope covers the systems the feature touches** — its Extension Points and End-to-End Flows usually name the integration points directly. Spot-check that the paths exist, then research only what a plan needs beyond them: how the app is built and tested, the real conventions and the closest feature to mirror, the concrete files and integration points, available dependencies, constraints from the agent instructions.
3. Size the research: `small` → inline; `medium` / `large` (or no Research Notes) → up to 3 **read-only** subagents returning findings and paths, not file dumps. Tell each one verbatim: *"Read-only: you may read, search and report. Do not edit or create files, and do not run builds, tests or any command that writes — not even into a build folder. If a fact needs a build or a test run to establish, report it as unknown and say which command would settle it."*
4. Sibling-skill pattern (e.g. bt-design's 3D-Hero-Scroll): read that skill's reference **and templates** *(where skills load through a tool: `load_skill` + `read_skill_resource`, never a guessed path; where they are files: the skills directory this skill was loaded from, e.g. `~/.claude/skills/`, `~/.agents/skills/` or the project's equivalent)*. The plan **copies and configures the template engine — never re-implements it**; each behavioral option the spec records (e.g. `sweep: page`) becomes an Acceptance item stated in observable terms. Prefer copying and wiring the template as the first task, so later tasks only configure it.
5. Too ambiguous to plan responsibly → ask the user. **Already built?** If the research shows some or all of the feature already exists, say so first and plan only what is missing (often just tests and the live check).

**Quick Plan (no spec file):** after the analysis, ask a small round of high-leverage questions (scope, behavior, edge cases, which systems it touches); skip anything the brief or code already answers. Unanswered items fall back to: feature name from the brief — the `<slug>`: lowercase kebab-case, `a-z 0-9 -` only, max 40 chars, with `-02`, `-03` … appended if a folder of that name already exists in `.agents/specs/`, `.agents/complete/`, `.agents/followup/` or anywhere under `.agents/archived/`; `spec_impact` and `size` inferred from the analysis; `proof: functional` unless `--parity`. List the assumptions in Codebase Analysis. **A Quick Plan is a creation point:** it first makes sure the default `.agents` folders exist — `.agents/specs/`, `.agents/complete/`, `.agents/archived/`, `.agents/followup/`, `.agents/profile/` and `.agents/recon/`, each with an empty `.gitkeep` (write only the ones missing; never touch what a folder holds), then creates the feature folder `.agents/specs/<slug>/` (with `documents/`), exactly as bt-spec would, and the plan, report and tests live there.

**A Quick Plan of follow-ups** (`Fix F3 from @<source-folder>/documents/<slug>_followups.md`, the dashboard's Quick Plan copy command): the cited follow-ups are the brief, read in full with what they point at in the source feature (its plan's Decisions, the run-log lines and files named, its `recon/` copies when they touch that code). Plan only them, as one new feature named for what they fix, never `fix-f3` or the source's slug. The plan's opening paragraph names them with the file: `Quick Plan for follow-up **F3** of <source title> (\`<source-folder>/documents/<slug>_followups.md\`).` — the helper's `check` links an unlinked feature from that line, so it must be there. A cited id the file lacks: list the ids it has, and stop. A cited follow-up whose **Status** line says a later feature already addresses it (anything but *partly done*): name that feature and ask before planning it again. Step 4 links the new feature to them.

**A Quick Plan of profile fixes** (`Fix F1 and F3 from @.agents/profile/<slug>/findings.md using @<recon>`, bt-profile's Quick Plan copy command): the cited fixes in `findings.md` are the brief — each one's cause, evidence, code, proposed fix, gain, risk and how to verify it, and the Verify becomes the task's proof. Read every cited recon in full, whatever its scope says, and **copy each into the new feature's `recon/` folder** (as bt-spec does), so the feature holds what it rests on after the profile is archived; turn what a recon says must not break into Acceptance or named tests. A cited recon that does not exist yet: say so, give its `/bt-recon` command (the report's **Copy recon command**), and carry on with your own analysis. Plan only the cited fixes, as one new feature named for what they fix, never `fix-f1` or the profile's slug; the plan's opening paragraph names them with the file (`Quick Plan for fixes **F1** and **F3** of profile <slug> (\`.agents/profile/<slug>/findings.md\`).`). Add a last task that re-profiles the same scenario (`/bt-profile --slug:<slug>`) and compares the phases the findings name — that re-measure is how the profile learns the fixes worked.

**The feature folder.** Every feature has one: `.agents/specs/<slug>/` holding `dashboard.html` (the feature dashboard), `documents/` (`<slug>_spec.md`, `<slug>_plan.md`, bt-execute's `<slug>_autopilot.md`, the dashboard data `<slug>_dashboard.js` and live status `<slug>_live.js`), `snapshots/` and `tests/`. From a spec, `<slug>` is its folder name. A **legacy flat spec** (`.agents/specs/<slug>_spec.md`) is read where it is and left there; the plan and report still go into the new `.agents/specs/<slug>/` folder, and the report's Spec link points back to the flat file.

## Step 2. Rules for a good plan

Execution time is mostly *how the work is proven*, not the code. Keep proof strong and cheap:

1. **Tasks are real units of work** — something a developer would commit on its own, with its tests. Guide: `small` 1–3 tasks, `medium` 3–8, `large` as needed. Merge tasks that touch the same code for the same purpose; split only when a task would not fit in one sitting. Going well past the guide needs a one-line reason in Codebase Analysis.
2. **Phases.** Group tasks under `### Phase N — <name>`. bt-execute runs one independent verifier per phase, once all its tracks are built. Small plan = one phase; otherwise 2–4 related tasks ending at a natural checkpoint. **A plan of 3 tasks or fewer runs inline**, and says so (Step 3).
3. **Tracks — parallel builders that never conflict.** Every task has a `Track:` letter; bt-execute runs one builder per track at the same time, each owning its track's files (Step 3 lists them). Tasks whose files overlap share a track; tasks that depend on each other share a track or sit in different phases. Within a phase, tasks are numbered in track order. A file two tracks need — a route table, `package.json`, a lockfile, a shared stylesheet, a test list — belongs to exactly one track, or to a short closing integration step the orchestrator runs after the tracks. Dependency changes (`npm install`) go to one track, before the others start, or to the integration step. Unity (or Blender) work for one project stays on one track — Unity holds one editor per project.
4. **`Verify level`** per task: `standard` (build, named tests, diff review) or `live` (needs the dev server, a browser, Unity or Blender to observe). Mark `live` whenever correctness shows only at runtime — rendering, UI, interaction, Unity↔Babylon parity. If a live check may be impossible where the plan runs (needs credentials, data or hardware), say in the task what to report instead.
5. **Verification — complete, never duplicated.** Acceptance names **every** requirement a user of the feature would notice, each **once**, as a checkable statement — no line cap. No Acceptance line repeats a check another task already proves; a read-and-confirm check belongs to the task that made the change. bt-execute's builder never re-proves the Acceptance live — the phase verifier is the only live checker. Every task keeps its own checks for what it changed, in its own phase, never deferred to a later one. A check that needs a costly session (several browser pages, a long play-through, a Unity re-export, a second engine) is planned **once per phase**: one session proves every task in that phase that needs it, and the tracks section says which. Never schedule a capture or page session **per task** in the Steps — the most expensive mistake this skill can make. The last feature task keeps a `live` end-to-end check of the whole feature when it has anything on screen, in its Acceptance (not a separate task) — in addition to the per-task checks, never instead.
6. **Named tests** with expected outcomes for every task that has a testable surface, in test files under the feature folder's `tests/` (`.agents/specs/<slug>/tests/` — never a root `tests/` folder). No probe suites, fuzzing or mutation testing unless the risk calls for it.
7. **Functional proof by default:** unit tests; for anything on screen, a look in the phase's shared session — the running result in the browser, judged against the spec and DESIGN.md, or beside a reference image when one exists (a mockup, the original site, the Unity view) — on one browser/engine at reduced resolution unless a requirement names another; cheap value fixtures sampled once from a reference implementation where there is one. **Numeric parity gates** (pixel thresholds, repeats, several engines) only under `--parity` / `proof: parity` or when the brief states a number — and then planned to run once per phase (iteration inside the phase uses the quick look), never loosened.
8. **Proportional safety.** When the spec requires a safety outcome (nothing unfinished reaches the user's folders, the app keeps working between tasks), pick the cheapest mechanism that achieves it — normally a build output the user's folders do not read, and one copy across at the end after the live check — never a branch or a commit (the user owns git). Add staged promotions, per-step archives or hash records only if the brief asks for them by name.
9. **Minimal exports.** A task's Steps re-export only the Unity project the task tests and only the scenes it works on, and only when the change alters that scene's export. Never write "re-export every scene" or "re-export all projects" for consistency — other scenes pick the change up at their next natural export. Name the scenes explicitly.
10. **No ceremony.** No standalone "verification sweep / open the review / final check" tasks, and no ledgers, md5 or environment records, archives, checked-in capture trees, standing evidence suites, doc-integrity registration or staged promotions — unless the brief asks.
11. **No brittle pins.** Never pin counts later tasks will change (tests passed, suite sizes, hashes). Say "the named tests pass, no new failures versus the baseline".
12. **Plan code follows the Agent Reference's Coding Practices — ENFORCED.** Every snippet, signature, interface, class, member, constant and file name the plan writes is clean, professional TypeScript or JavaScript in the project's language (never switched unasked), with meaningful full-word names (no one- or two-letter names, cryptic abbreviations or code-golf tricks), well structured, readable and maintainable by human developers, with meaningful JSDoc on every class, function, method, interface and public member. JSDoc is never a gate: no Acceptance item, Test or Verify step fails on missing JSDoc. The executor copies plan code word for word, so a badly named snippet ships badly named. Names that bind to exported data (component properties, serialized fields, Unity property names) keep the source's names. Plan UI code also follows **Game UI Performance — ENFORCED**: every HUD value is classified as *state* (React, set on events) or *telemetry* (refs and one frame loop, never React state or a per-frame EventBus message), and the snippets show telemetry that way. Every UI element gets the cheapest cadence in `ui-design-system.md` › **Per frame or not** — events for state, CSS for decorative motion, the frame loop only for telemetry, throttled readouts, nothing while hidden — and no snippet puts a frame loop on a menu, splash, preloader or landing page (a real-time hero excepted, paused off-screen and at rest). Code-quality checks are never a separate task; bt-execute's verifier enforces them on every task.

## Step 3. Write the plan

Print `✍️ [bt-plan] Writing .agents/specs/<slug>/documents/<slug>_plan.md …`. The file has, in order:

**`## Codebase Analysis`** — what Step 1 found, citing real files; the SPEC.md sections the plan conforms to; `spec_impact`, `size`, `proof` (say which were inferred); Quick Plan assumptions.

**`## Tasks`**

```markdown
### Phase 1 — <name>

- [ ] **T1** — <short imperative title>
  - Track: A
  - Files: `path/one` (create), `path/two` (modify)
  - Details: <what to do>
  - Tests: `.agents/specs/<slug>/tests/<test file>` — `<case>` → <expected outcome>; …   (or "no testable surface — <why>")
  - Acceptance: <every requirement this task delivers, each once, as an observable, checkable statement>
  - Verify level: standard
```

**`Update SPEC.md` — the last task, when the feature is spec-impacting** — `spec_impact: yes`, or your analysis found it adds or changes a system, convention, dependency or architectural decision (otherwise state in Codebase Analysis that none is needed):

```markdown
- [ ] **T<n>** — Update SPEC.md to match what was built
  - Track: integration (after every track of its phase is built)
  - Files: `SPEC.md`
  - Details: Update the sections named in the spec's Project Spec Alignment, following SPEC.md's "How to update this spec" (replace/merge current-state sections; append Decisions). Record the product only — never verification procedure, tool lists, ledgers or gates.
  - Acceptance: SPEC.md matches what the tasks above shipped; new dependencies listed; nothing contradicts the code.
  - Verify level: standard
```

**`### Tracks and owned files`** — closes `## Tasks`. Per phase: each track's tasks and owned files; who owns each shared file (a track, or the integration step); which track installs dependencies or drives each Unity project; each shared costly session and the tasks it proves:

```markdown
- Phase 1 — **A (T1, T2):** `path/one`, `path/two` · **B (T3):** `path/three` · integration (orchestrator, after the tracks): `package.json` · shared session: one browser session proves T2 and T3.
```

A plan of 3 tasks or fewer writes instead: `Runs inline — bt-execute builds these tasks itself and runs one independent verifier at the end.`

**`## Estimated execution time`** — **agent time, from the calibration below — never developer-hours, and never by adding up activities.** Builds, exports, captures and browser looks are *not* separate line items: they happen inside a task's run and its rate. Counting them separately is how a 10-hour plan gets estimated at 45 hours.

Rate each task by the **kind of work it does** (classify tasks, not the plan — most plans mix kinds), sum, then give a range of **−35 % / +50 %**. Nothing else is added — no per-phase overhead (it did not show up in the measurements):

| Kind | min/task (provisional) | What puts a task here |
| --- | --- | --- |
| **Code** | 5 | Code + tests, at most a quick browser look or one small scripted export. |
| **Live** | 10 | Proven by running it: live external APIs, a page or scene loaded and probed in a browser, live memory or perf runs in one engine, a visual match to a reference image. |
| **Game** | 25 | Proven by **playing the running game**: races, laps or levels driven through scenarios, a two-page network session, reproducing an intermittent in-game bug, tuning feel or sound by eye and ear. |
| **Unity / parity / GPU** | 25 | Authoring or re-exporting Unity content, measured parity against Unity Play mode, GPU shader backends, perf A/B across beds, exporter DLL + runtime changed together. |

- **Live or Game?** Loading a scene and reading values from it is Live. Playing it until something happens is Game. Game work ran 1.2–2.8× its estimate when rated Live: every scenario is a real-time play session, and a bug that shows on lap three costs three laps per check.
- **Do not budget fix rounds.** They are inside the rates (about one task in four needed a second attempt); budgeting rounds per phase was the largest source of over-estimation in the first calibration.
- **Do not add a further margin.** The range is the margin. Do not discount for parallel phases or tracks either — the rates are wall-clock with bt-execute's usual parallelism.
- **Outsized work is 2× the task's own kind rate**, never a flat figure. A task that ports a whole engine subsystem rated as Code is 10 min, not the Unity rate doubled. A task that builds a compiler or transpiler, or must prove coverage across many Unity sample projects, is 2× Unity (shadergraph-transpiler-complete-coverage ran 72 min/task on the earlier loop). Multiply by ~2 for `proof: parity` only if the plan really carries numeric gates, and by ~2–3 for `bt-execute --strict` (neither measured yet).
- **Unity frame-matching runs long.** A task proven by matching Unity frame by frame (animation feel, foot IK, landing poses) is where Unity tasks overran most (starter-assets-third-person: 2.4×). Name it as the biggest uncertainty.
- **The estimate covers the plan as written.** Tasks added mid-run cost far more than planned ones — unity-terrain-system-parity's 17 planned tasks took about 6 h, the 9 added during the run about 21 h. Say so in the biggest-uncertainty line when the scope is still moving. Tasks added after a plan is complete get their own estimate at these rates.

**Calibration — provisional lean rates (2026-10-25).** Not yet measured, they replace the third calibration's Code 6 · Live 16 · Game 40 · Unity 35 (2026-10-19, 40 runs of the pre-lean loop). **Re-fit them from the `⏱` lines of the first five lean runs**, then drop "provisional".

To re-fit: read the `⏱` lines bt-execute writes to each `documents/<slug>_autopilot.md` — the plan's estimate, active minutes per phase and per run, waits already separated out. Take active time only; count each run's tasks by kind (outsized 2×) and fit a rate per kind on lean runs only, leaving out runs whose scope grew mid-run, reopened deferred tasks and user-directed follow-ups. Aim for a median actual ÷ estimate near 1.00 with most runs inside −35 % / +50 %; then update the table and this paragraph.

Write a table `Phase | Tasks | Kind (code / live / game / Unity) | What makes it slow | Estimate`, then one **Total** line in hours (days only if over ~16 h), the `--strict` multiplier, and the biggest uncertainty in one line. If the total averages above ~30 or below ~5 min per task, the estimate is wrong before the plan is: re-check it. An estimate, never a pin.

**`## How to execute this plan`** — this text verbatim:

```markdown
## How to execute this plan

Each task above is a checkbox. To implement:
- Run a single task with the bt-execute command (e.g. `bt-execute <this-file> T<n>`), run every remaining task in order with `bt-execute <this-file> ALL` (resumable — it skips tasks already checked), or implement the whole plan from a prompt like "implement the plan at <this-file>".
- bt-execute verifies each phase with an independent verifier; add `--strict` for an adversarial verifier on every task.
- Work the tasks top to bottom — bt-execute builds a phase's tracks in parallel — unless a task notes a different dependency order.
- When a task is fully implemented and its **Acceptance** criteria are met, mark it complete by editing this file and changing that task's `- [ ]` to `- [x]`.
- Stop and report if a task cannot be completed. Do NOT check a box for partial, skipped, or unverified work.
```

## Step 4. Write and check the dashboard (planned state)

Print `🗂️ [bt-plan] Writing the feature dashboard …`. **A spec from bt-spec already has a dashboard, in its `specified` state** (showing the bt-plan commands): read its `<slug>_dashboard.js` first and keep its `feature` (with any `addresses` — the follow-ups it takes on), `decisions`, `activity` and any **Source follow-ups** document link; everything below then fills it in and moves it to `planned`. A Quick Plan, or a spec with no dashboard, creates it here. From bt-execute's `templates/dashboard/` *(where skills load through a tool: `load_skill('bt-execute')` + `read_skill_resource`; where they are files: the sibling `bt-execute/` folder in the skills directory this skill was loaded from)*:

- copy `dashboard.html` to `.agents/specs/<slug>/dashboard.html`, replacing `{{slug}}` with the slug and changing nothing else (always — over a copy bt-spec wrote too, so the page is the current template);
- write `.agents/specs/<slug>/documents/<slug>_dashboard.js` from the starter `dashboard.template.js`, written whole as strict JSON behind its `window.FEATURE_DASHBOARD =` prefix — double-quoted keys, no comments, no trailing commas (`data-schema.md` documents every field): `feature` (title, slug, branch, `origin` `spec` or `quick-plan`, size, proof, a plain-language summary), `documents` (Spec — omitted for a Quick Plan — and Plan), `status: "planned"`, `updatedAt` from the shell clock (`date '+%Y-%m-%d %H:%M'`; with no shell, the current local time), `estimate` (the Total line), every phase and task from the plan as `pending` (id, title, kind from the estimate table, verify level), an empty `afterAction` and no snapshots, the plan’s Decisions as `decisions` (Heavy Plan; otherwise the spec’s), each an object `{ "id": "D1", "text": "…", "updates": [] }` (never a plain `"D1 — …"` string, which shows as an empty row), and one more `activity` line: `Plan written — <n> tasks in <k> phases, estimated <range>` (after bt-spec's `Spec written` line when there is one);
- write `.agents/specs/<slug>/documents/<slug>_live.js` from `live.template.js`, the same way (whole, strict JSON): no task, `role: "orchestrator"`, `title: "Plan written — waiting for bt-execute"`, no steps (bt-execute's helper rewrites it with every task update).
- in a git repository, make sure `.gitignore` (at the repository root) contains the line `.agents/*/*/documents/*_live.js` — append it once if missing. The live file is not history worth keeping; `<slug>_dashboard.js` is, and stays tracked. A live file git already tracks is left alone.

Re-planning an existing feature rewrites the data file's phases and tasks from the new plan but keeps the results of tasks already done, its `afterAction` and its `activity` history, adding a `Plan revised` line; new tasks are `pending` with an `updates` note, and a `complete` status becomes `paused`. The dashboard is a deliverable: if the template cannot be found, say so and stop — the plan is not finished until the check below passes.

**A Quick Plan of follow-ups**, once its dashboard is written: from the project root, run `node <skills>/bt-execute/scripts/dashboard.mjs addresses .agents/specs/<slug> --source <source-folder> --ids F3[,F5]`. It records on this feature which follow-ups it takes on and links their document, and marks them **Planned** on the source dashboard with a link back here; bt-execute then carries the feature's progress to them (in progress, done). It fails on an id the source lacks — fix the ids, never skip it. (A plan of a spec bt-spec made from follow-ups is already linked; its `addresses` stays in `feature`.)

**Check, then stop.** Run `node <skills>/bt-execute/scripts/dashboard.mjs check .agents/specs/<slug>` (`<skills>`: the skills directory this skill was loaded from). It fails when a deliverable is missing — a dashboard file absent, or the dashboard's tasks out of step with the plan's checklist (ids and order) — or a data file is malformed. Fix what it names and re-run; **never finish while it fails**, whoever wrote the plan — this skill or an agent by hand. Where Node cannot run the helper, make the same checks by reading the files, and say so.

Then **stop**. Final message: a short summary, the estimated time, and:

```
Plan written to .agents/specs/<slug>/documents/<slug>_plan.md — <n> tasks, estimated <total range> of agent time
Dashboard: .agents/specs/<slug>/dashboard.html (open it in a browser to copy a bt-execute command; bt-execute keeps it current)
Run a single task with `bt-execute .agents/specs/<slug>/documents/<slug>_plan.md T1`, or every task with `bt-execute .agents/specs/<slug>/documents/<slug>_plan.md ALL` (add `--strict` for an adversarial verifier on every task).
```

## Heavy Plan mode (`--heavy`)

Use when the plan will be executed in fresh contexts, over days, or by a cheaper model than the one planning. The plan file is then the only memory that survives between tasks: **whatever it does not say, task 40 will re-decide differently from task 3.** So a heavy plan decides everything once, in one place, and every task cites it. Print `🏋️ [bt-plan] Heavy Plan mode`. Everything above still applies; the document gains two sections and richer task blocks. There is no limit on how much a heavy plan may say — write what the executor needs — but the number of tasks still follows the spec's `size`.

In Step 1, collect plan-grade detail: `file:line` references, the real signatures the feature calls or changes, verbatim 10–30-line snippets of the conventions to mirror, the exact API usage from the Agent Reference sub-documents, the Agent Reference's full `Coding Practices — ENFORCED` section, and the test baseline (command, current state, pre-existing failures). Carry the spec's Decisions forward and resolve every Open Question — with the user if needed. "TBD", "as appropriate", "the implementer may choose" are forbidden.

Sections, in order: `## Codebase Analysis` (plus the test baseline) · **`## Decisions`** · **`## Design Reference`** · `## Tasks` · `## Estimated execution time` · `## How to execute this plan`.

- **`## Decisions`** — numbered `D1, D2 …`, one per choice that binds more than one task or rejects a plausible alternative — architecture, file layout, naming, algorithms and constants, error policy, dependencies (exact packages and versions, or "no new dependencies"), sibling-skill option values, test strategy:
  `- **D3 — <decision, stated as a fact>.** <why / precedent with file:line> Rejected: <alternative> (<why not>). Binds: T4, T7.`
- **`## Design Reference`** — the shared blueprint, written as code wherever the code *is* the decision: File map (path · create/modify/delete · responsibility · tasks) · Module boundaries · Interfaces & contracts (full signatures, in the project's language) · Data shapes & state · Control flow · Algorithms & formulas with their constants · Error & edge-case policy (`when X → Y`) · Conventions to mirror (verbatim, with `file:line`) · API usage · Test strategy. Omit a heading only if it truly does not apply. **All of it is written to the Agent Reference's Coding Practices — ENFORCED**: every interface, signature, data shape, constant and snippet uses meaningful full-word names, strict types (JSDoc type tags in JavaScript) and meaningful JSDoc, and reads cleanly to a developer new to the project. Mirror the structure of existing conventions, but never copy one- or two-letter names or obfuscated code into a new name.
- **Heavy task block** — adds to the standard block: `Depends on:` (same track, or an earlier phase) · `Applies:` (the D-numbers and Design Reference entries it must match) · `Steps:` numbered instructions, each naming the file, a real anchor (prefer quoted code over bare line numbers) and the change · `Code:` when the code is the decision, written to the Coding Practices exactly as it must ship · `Do not:` the tempting wrong turns · `Verify:` commands with expected output. `Depends on`, `Files`, `Applies`, `Steps`, `Tests`, `Acceptance`, `Verify` and `Verify level` are required on every heavy task. A task never says "like T3" — it cites the Design Reference; a name, signature or value a step introduces is added to the Design Reference first, so task 40 types what task 3 typed. Say what keeps the app working between tasks (shim, flag) and which task removes it. The `Update SPEC.md` task carries the exact text to write.
